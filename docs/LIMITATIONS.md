# Known limitations — not launch complete

- This checkpoint is partial software, not full iLovePDF/CamScanner parity or a production release.
- Core Linux tests do not establish Windows or Android compatibility. No clean-device validation.
- PDFium and SQLite are now integrated on the tested Linux host. OpenCV geometry has a separately tested development candidate with manual corners, perspective and advisory edge suggestions; it is not staged in current downloads. Deskew and face assistance remain unimplemented. The Linux implementation integrates Tesseract with typed editable plain-text results and verified English/Bangla models, but requires the separately installed system engine. Windows/Android OCR, searchable PDF geometry and representative accuracy/performance validation remain unavailable. Current saved downloads have no perspective correction or face detection. Manual Android camera capture compiles through a scoped system-camera adapter, but device behavior remains unverified. Local scan draft recovery is implemented. SQLite theme persistence is implemented; history recording remains off in the UI.
- PDF manipulation rejects unsupported structures; no forms, annotations, bookmarks, attachments, digital signatures, optional content or tagged documents. Supported simple PDFs can be arranged, visibly numbered/watermarked and read as editable plain text. Watermarks currently accept visible ASCII only. Text-layer extraction can miss glyphs or differ from visual reading order, and is bounded to one million counted characters and4MiB of saved UTF-8; image-only scans need separately available OCR. No render/appearance guarantee for arbitrary PDFs.
- PDF parsing is in-process. Encoded-size, page-count, object-count and nesting checks do not provide hard protection against decompression bombs or parser resource exhaustion. Process isolation is a production blocker.
- Photo inputs are JPEG/PNG, up to 24 megapixels/64 MiB. ICC profiles are rejected rather than silently changed; unprofiled pixel data is assumed sRGB. PNG gamma/chromaticity policy needs fuller validation. No flexible-dimension compression yet.
- Background removal is a brightness threshold for plain backgrounds, not ML segmentation; no manual refinement UI. Dark backgrounds and shadows may need external correction.
- No secure redaction, encryption/unlocking, certificate-backed signing, Word conversion, remote AI, cloud synchronization or monetization.
- Declarative recipes/core batches and print layouts exist; editing/persistence and serial batch retry interfaces are implemented; broader recipes remain.
- Application pack UI is an explicitly unverified example with fixed photo/signature geometry. It does not claim compliance with any official application.
- Android content-provider saving compiles in the built APK but is not device-tested. Camera cancellation/denial and activity-recreation flows need device testing. Desktop save-copy is tested.
- Linux GUI release bundle compiles and its release bridge passes tests. Packaged Linux GUI startup passed on an Ubuntu 24.04 hosted virtual display; local display restrictions still prevent interactive inspection here. Windows ZIP and Android APK builds passed hosted gates. Windows startup created a window; clean-device and complete interactive workflows remain unverified.
- History/signature retention is not enabled; reusable local signature storage is not implemented. No promise of physical secure erasure.

- OCR resource limits apply to the child, not all parent-side image preparation. They do not establish a filesystem/network sandbox. Cancellation waits for preparation checkpoints; the engine is killed/reaped before a cancelled return. Abnormal parent termination can leave private temporary files; abandoned-job retention/cleanup is still pending. The engine-presence/model-hash capability check is not an engine-version certification.

- Physical-photo mm/DPI export is implemented locally with pixel rounding, verified JPEG JFIF/PNG pHYs and preserved 16-bit PNG where applicable. UI reports the saved size; external print settings can change final dimensions. This is not printer/official-application acceptance certification. Main28163d4 platform package checks passed; clean-device and printer acceptance remain outstanding.

- Scanner encoded image/PDF budgets and sequential preparation are tested locally. They do not cap all process memory: decoded transformations, originals, PDF objects, output and bridge copies can coexist. Native parser isolation remains a production blocker. New scanner packaging must pass before its development downloads are updated.

- Export names reject Windows reserved device names, including COM/LPT with superscript ¹/²/³ (Microsoft primary naming documentation checked 2026-10-18: https://learn.microsoft.com/en-us/windows/win32/fileio/naming-a-file). Bangla names remain accepted without renaming. This is not a claim of identical filename/collision behavior across every document provider or filesystem.

- Custom print-sheet controls are implemented/tested on work/print-layout, with source pixels preserved by default and optional explicit resampling. They are not in the saved main27c8b3d builds until the candidate is packaged and integrated. Printer output remains unverified.

- Streaming image encoding on work/image-encoding-limits removes full PNG compressed/pixel-copy intermediates and enforces encoded byte budgets while writing. Core and interface checks pass locally; platform packaging is pending. This is not a hard application-wide memory limit or hostile-parser sandbox.
